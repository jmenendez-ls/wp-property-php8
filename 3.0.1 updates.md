# WP-Property 3.0.1 — WordPress 6.7+ textdomain timing fixes

This release is a local patch on top of **WP-Property 3.0.0**. It removes `_doing_it_wrong()` notices introduced in WordPress 6.7 when the `wpp` text domain is used before the `init` action. No user-facing behavior is intentionally changed; translated strings still appear once WordPress has finished loading translations.

## Background

WordPress 6.7 warns when `__()`, `_e()`, and related functions run for a plugin text domain before `init`. WP-Property’s bootstrap runs on `plugins_loaded` (priority 100), which is earlier than `init`. WordPress reports only the first early call per request, so the call sites were found in two rounds. The first round fixed these three:

1. **`Bootstrap::get_localization()`** — called from `get_schema()` while `composer.json` schema strings are localized during plugin load.
2. **`Settings::__construct()`** — built the `descriptions` settings array with `__()` when settings are first initialized.
3. **`UsabilityDynamics\UD_API\Client::request()`** — default `product_name` in `wp_parse_args()` used `__()` for licensing/update API requests that can run before `init`.

The second round fixed the remaining `Settings` constructor defaults, the `Attributes` type labels, and the `lib-ud-api-client` license screen labels (sections 2, 3a and 3b).

## 1. `lib/classes/class-bootstrap.php`

### `boot()` — reset cached schema on `init`

**Change:** At the start of `boot()`, register:

```php
add_action( 'init', function () {
  $this->schema = null;
}, 0 );
```

**Why:** `get_schema()` caches localized schema in `$this->schema` the first time it runs. If that happens before `init`, `get_localization()` must return English strings (see below). Clearing `$this->schema` at the beginning of `init` forces the next `get_schema()` call to rebuild the cache using translated strings after the text domain is allowed to load.

The `$schema` property is defined on the parent `UsabilityDynamics\WP\Bootstrap` class and is safe to reset.

### `get_localization()` — defer translation until `init`

**Before:** Always returned:

- `licenses_menu_title` → `__('Add-ons', $this->domain)`
- `licenses_page_title` → `__('WP-Property Add-ons Manager', $this->domain)`

**After:** If `did_action( 'init' )` is false, return the same English literals without calling `__()`. After `init`, use `__()` as before. The `wpp::get_localization` filter still wraps the array.

**Why:** `get_localization()` feeds `Utility::l10n_localize()` when `composer.json` schema is read during early bootstrap (including plugin inclusion). Skipping translation before `init` avoids the notice; schema is corrected after `init` when the cache is cleared.

## 2. `lib/classes/class-settings.php`

### Constructor — remove early `__()` for descriptions

**Change:** Removed the block that set `$data['descriptions']` with three `__()` / `sprintf( __() )` strings during construction. Registered instead:

```php
add_action( 'init', array( $this, 'apply_translated_defaults' ), 0 );
```

### New method `apply_translated_defaults()`

**Change:** On `init` (priority 0), calls `$this->set()` with the same nested structure as before:

- `descriptions.descriptions.property_type`
- `descriptions.descriptions.custom_attribute_overview`
- `descriptions.descriptions.tagline`

Then refreshes the global `$wp_properties` from `$this->get()`.

**Why:** Settings are constructed in `Bootstrap::init()` on `plugins_loaded:100`, still before `init`. Moving these admin helper strings to `init` matches WordPress’s textdomain rules while preserving the same copy in the admin UI once the page loads.

### Constructor "STEP 3" defaults

**Change:** `property_types`, `property_assistant`, `property_stats` and `search_conversions` defaults now use plain English strings in the constructor (same conditions as before), and each key that was set is recorded in `$this->untranslated_defaults`. `apply_translated_defaults()` re-sets those keys with the `__()` versions on `init:0`.

**Why:** These run on sites whose stored `wpp_settings` don't trigger the constructor's early return (the production site), which is why the notice came back after the first round of fixes.

## 3a. `lib/classes/class-attributes.php`

**Change:** The attribute type labels and `set( 'attributes.types', … )` moved from the constructor into `register_attribute_types()`, hooked on `init:0`.

## 3b. `vendor/libraries/usabilitydynamics/lib-ud-api-client/lib/classes/class-admin.php`

**Change:** License screen labels ("Licenses", "More Products") moved into `get_screens( $translate )`. Before `init` they are untranslated, and `UI::available_screens` is refreshed with translated labels on `init:0`. This path only runs on admin and AJAX requests.

See `docs/wp-property-textdomain-fix.md` in the project root for before and after snippets and how all early calls were traced.

## 3. `vendor/libraries/usabilitydynamics/lib-ud-api-client/lib/classes/class-api.php`

### `request()` — conditional default `product_name`

**Before:**

```php
'product_name' => __( 'UsabilityDynamics Product', $this->domain ),
```

**After:**

```php
'product_name' => did_action( 'init' ) ? __( 'UsabilityDynamics Product', $this->domain ) : 'UsabilityDynamics Product',
```

**Why:** Licensing and update checks may call `request()` before `init`. The product name is sent to Usability Dynamics’ remote API as metadata, not shown in the UI. Using the English default pre-`init` is harmless; after `init`, behavior matches the previous translated default.

**Reapply note:** This file lives in the vendored `lib-ud-api-client` package. Reinstalling or updating that dependency without reapplying this one-line change will bring the notice back.
